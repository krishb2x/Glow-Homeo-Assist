## 1. Product framing

GlowHomeo Assist is a **B2B clinic management platform for homeopathic
practices**. It is built for the **doctor** as the primary user, with
admin and (later) patient roles layered around the core consult flow.

The product blends three patterns from modern healthcare SaaS:

| Pattern from… | What we take                                                      |
| ------------- | ------------------------------------------------------------------ |
| Jane App      | "Smart" SOAP/case notes generated by AI from session audio, with the doctor as final reviewer. Customizable per-template prompts. (50%+ charting time savings reported by Jane in 2026.) |
| Carepatron    | AI scribe **right-side drawer** during video calls; chart, past notes and templates accessible *without leaving* the session. |
| Teladoc Solo  | Split / picture-in-picture video so the chart is **never hidden** during a tele-consult. |
| FHIR (subset) | Conceptual model: `Encounter → Observation → Condition → MedicationRequest → CarePlan`. We don't ship FHIR R4 on day one, but our internal model is FHIR-shaped so we can export later. |

Key product invariants:

- **The doctor always signs the note.** AI drafts, doctor finalizes.
- **No fake data in the production UI.** Demo mode is a separate flag.
- **Prescriptions are created only from inside a finalized consultation.**
- **Privacy first:** raw audio is short-lived; transcripts and notes are the durable record.
- **Mobile patient app is explicitly out of scope for v2.** The web doctor app must work standalone.

## 3. Bounded contexts (modules)

We split the backend by **bounded context**, not by HTTP layer. Each context owns its DB tables, its API route prefix, and its background jobs.

| Context             | Owns                                                         | API prefix                  |
| ------------------- | ------------------------------------------------------------ | --------------------------- |
| **identity**        | `clinics`, `profiles`, RBAC helpers, invites                 | `/doctor/me`, `/admin/users` |
| **patients**        | `patients`, demographics, allergies, tags                    | `/doctor/patients`          |
| **encounters**      | `consultations` (= encounters), `clinical_record` JSON, lifecycle | `/doctor/consultations` |
| **observations**    | structured findings (symptoms, vitals, mental/emotional)     | (nested under encounter)    |
| **media**           | `audio_sessions`, `media_objects`, signed URLs               | `/doctor/audio`             |
| **ai_scribe**       | `scribe_jobs`, prompts, drafts vs final                      | `/doctor/scribe`            |
| **prescriptions**   | `prescriptions`, items, branding, PDFs                       | `/doctor/prescriptions`     |
| **continuity**      | `appointments`, `follow_ups`, `case_outcomes`                | `/doctor/follow-ups`, `/doctor/appointments` |
| **communications**  | `messages`, `notification_jobs`                              | `/doctor/messages`          |
| **library**         | `advice_templates`, `treatment_plans`, `remedies`            | `/doctor/library`           |
| **billing**         | Plan, seats, invoices *(phase 2)*                            | `/admin/billing`            |
| **audit**           | append-only event stream                                     | `/admin/audit`              |

> The current code already realises most of these contexts inside
> `apps/api/src/server.ts` and the `homeosyncDoctorApi.ts` file. The
> v2 refactor splits each into `apps/api/src/modules/<context>/`.

### 4.1 Behavior contracts

- **Progressive disclosure.** Steps appear in order, but they live in a single scrollable feed (Carepatron-style). The step rail on the left is an anchor menu — clicking jumps + collapses unrelated sections.
- **Prior outcome check is inline.** When a returning patient is opened, the dashboard shows a **non-blocking inline strip**: "Did the last remedy work?" → tap a chip (Cure / Improvement / Palliation / No change / Worse) → answer is saved as a `case_outcome` row referencing the **previous** consultation. Only after that does the new consult activate; no modal.
- **AI Scribe drawer is hidden by default.** Doctor opens it from the right rail. When the mic is recording, the drawer shows the rolling transcript; when stopped, it shows the AI-drafted note pieces that the doctor can "insert" into the chart.
- **No autosave fake spinners.** Saving is debounced (1.5 s) per section; status shown as `Saved · 2s ago` text near the footer.
- **Keyboard:** `Alt + ←/→` jumps steps, `Alt + R` toggles recording, `Alt + I` opens AI drawer, `Cmd/Ctrl + Enter` finalizes.
- **Finalize is irreversible.** Sets `lifecycle_status = FINALIZED`, locks the chart, triggers PDF render, opens the follow-up drawer.

### 4.2 Online vs in-clinic

Both modes share the same shell. The left column swaps between:

- **Video tile** (online consult) — WebRTC peer connection + bandwidth-aware fallback to audio-only.
- **Past-visit reel** (in-clinic) — last 3 visits with thumbnails of remedy + outcome chip.

The footer + step rail + chart feed do not change.

## 5. Data flow scenarios

### 5.1 Starting a consultation

```
User clicks "Start consult" on PatientVisitCard
  → POST /doctor/consultations { patientId, type, mode }
    → API: insert consultation (lifecycle_status=ACTIVE)
    → API: write audit.consult_started event
    → API: returns { id, patient, priorOutcomePending }
  → Web: route to /consultation/[id]
  → Web: if priorOutcomePending => render inline outcome strip (step 1)
```

### 5.2 Live AI scribe

```
Doctor opens AI drawer → presses ⏺
  → Web: navigator.mediaDevices.getUserMedia()
  → Web: WebSocket /audio/stream?consultationId=...
    → API audioStream/consultationWss.ts authenticates
    → forwards PCM frames to Gemini Live (if GEMINI_API_KEY)
       or to deterministic mock pipeline
    → emits partial transcript events back on WS
    → on stop: produces structured note draft
       (chief complaint / history / mind / Rx hints)
  → Web: drawer shows transcript live; "Insert" buttons for each draft piece
  → Web: on Insert, PATCH /doctor/consultations/:id/clinical-record
       (server enforces JSON shape via Zod + version increments)
```

### 5.3 Finalize → PDF → follow-up

```
Doctor clicks Finalize
  → POST /doctor/consultations/:id/finalize
    → API: validate prescription items + advice exist
    → API: insert prescription row, lifecycle_status=FINALIZED, finalized_at=now
    → API: enqueue pdf_render job (prescription + case_summary)
    → API: enqueue notification_job (WA/email patient — phase 2)
  → Web: open Schedule-Follow-up drawer (default = +14 days, doctor confirms)
  → Worker: render PDF via Puppeteer template, upload to storage.pdf,
            insert media_objects row, mark consultation pdf_ready=true.
```

### 5.4 Audio purge

```
Cron: every hour
  → SELECT audio_sessions WHERE created_at < now() - interval '7 days'
       AND deleted_at IS NULL
  → For each: storage.objects delete + UPDATE audio_sessions SET deleted_at=now()
  → Write audit.audio_purged
```

## 6. Security & privacy

| Area              | Decision                                                                              |
| ----------------- | ------------------------------------------------------------------------------------- |
| AuthN             | Supabase Auth (email/password, magic link). Web stores JWT in httpOnly cookie.        |
| AuthZ             | Postgres **RLS** is the primary boundary. API uses the user's JWT (no service role)  except for admin/scribe jobs. |
| Tenancy           | Every domain table carries `clinic_id`. Helper `current_profile_clinic_id()` gates RLS. |
| Doctor-vs-doctor  | Patients have `assigned_doctor_id`; RLS hides others' patients unless `role='admin'`. |
| Audio             | PCM frames are **not persisted** by default. The `audio_sessions.recording_object_key` is set only when the doctor toggled "save audio." Auto-deleted after 7 days unless flagged. |
| Transcripts       | Stored encrypted-at-rest by Supabase; tied to `consultation_id`.                      |
| PHI in logs       | API logger (`apps/api/src/lib/logger.ts`) redacts `phone`, `email`, `name`, free-text fields. |
| AI provider       | All Gemini requests go through `apps/api`. Browser never holds the key.               |
| PDFs              | Stored in private bucket; signed URLs expire in 15 minutes.                           |
| Audit             | Append-only `audit.events` table, never updated from the API path.                    |
| Backups           | Supabase point-in-time recovery (7 days minimum on Pro plan).                         |
| Region            | Single region (India / ap-south-1) for v2; multi-region post-PMF.                     |

## 8. Deployment

```
GitHub (main)
   │
   ├──► Vercel  (apps/web)   — preview per PR, prod on tag
   │
   └──► Fly.io  (apps/api)   — autoscale 1–3 machines, region: bom
                                       │
                                       └── Supabase project (managed PG)
```

- One env-per-stage (dev / staging / prod) with separate Supabase projects.
- Secrets in Vercel / Fly.io vaults; **no `.env` in repo** (only `.env.example`).
- DB migrations via `supabase db push` from CI on protected `main` only.
- Audio purge + follow-up nudge run as Fly.io scheduled machines, sharing the API image.

## 10. Open questions (need confirmation before phase-2 code)

1. **Video provider:** Cloudflare Calls (cheap, raw WebRTC) vs LiveKit (feature-rich, SFU). Default proposal: **Cloudflare Calls** for cost.
2. **PDF engine:** Puppeteer-on-Fly vs PDFKit-in-process. Default proposal: **Puppeteer in worker dyno** — better template fidelity.
3. **Pre-consult patient intake form:** keep out of v2 or include? Default: **out of v2.** Doctor enters data.
4. **Outcome chip placement:** dashboard banner vs inside patient hub. Default: **inside patient hub + dashboard "needs your input" lane.**
5. **Repertorisation / Materia Medica:** ship a curated 130-remedy list now, full repertory later? Default: **yes, ship curated list; build full repertory in phase 5.**

These are flagged in `02_FOLDER_STRUCTURE.md` / `03_SCHEMA.md` as `TBD-Q#`.
